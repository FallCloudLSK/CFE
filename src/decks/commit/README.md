# 2026春季盃 牌組承諾（加密提交）系統

選手賽前線上提交「提交碼」，四強時提供「解鎖金鑰」公開牌組。主辦方在解鎖前無法得知牌組，選手提交後也無法換牌。全部在瀏覽器內運算，不需要伺服器，可直接放上 GitHub Pages。

| 檔案 | 用途 |
|---|---|
| `submit.html` | 選手用：以牌組編輯器介面編輯牌組、輸入參賽ID，產生提交碼與解鎖金鑰，並開啟 Google 表單確認提交 |
| `reveal.html` | 主辦方用：登錄時檢查提交碼格式（可批次）；四強時輸入金鑰解鎖並以牌組編輯器樣式顯示牌表 |
| `cfe-commit.js` | 共用的編碼與密碼學程式（演算法公開） |
| `style.css` | 共用樣式 |

---

## 一、原方案分析

原構想：①（牌組碼 + 自訂金鑰 + 固定字串）加密成密文 A；②（固定驗證文字 + A + 雜湊）以參賽 ID 加密成密文 B；登錄時解 B 驗證結構，四強時用金鑰解 A。

**大方向正確**（先提交、後揭露），但有四個關鍵問題：

1. **網頁原始碼是公開的，固定字串與公式藏不住。** 放在 GitHub Pages 的 JavaScript 任何人都能看到。選手可以照著公式自己做出「看起來像官方產生」的 B，裡面包任何內容，包括不合法的牌組。所以第②步的結構驗證**無法保證**「能解出合法牌組」。
2. **以參賽 ID 加密的 B 層沒有保密作用。** 主辦方知道 ID，可以直接解開 B 拿到 A，這層只是格式包裝。
3. **一般加密不具「綁定性」，選手可以事後換牌（最嚴重）。** 對沒有完整性保護的加密（例如 XOR、AES-CBC/CTR），換一把金鑰去解同一份 A，就會得到另一串明文。每 10,000 串隨機 10 碼約有 1 串剛好是合法牌組（合法牌組約 8.2×10¹³ 種，10 碼空間約 8.4×10¹⁷），選手可以在家離線試金鑰，預先準備好「解出牌組 X 的金鑰」和「解出牌組 Y 的金鑰」，到四強再看對手決定交哪一把。就連 AES-GCM 也已知可以做出能被兩把金鑰解開的密文，所以必須另外加上綁定牌組的雜湊。
4. **選手自訂金鑰太弱，主辦方可以猜。** 生日、暱稱這類金鑰可以字典暴力試；而且「解出來是不是合法牌組」本身就能篩掉大部分錯誤的猜測。反過來，如果雜湊驗證碼是直接對牌組算的，主辦方只要窮舉 8.2×10¹³ 種牌組逐一比對雜湊（一張顯示卡幾小時內就能跑完，主流牌型更少）就能得到牌組。

結論：**安全性只能建立在「足夠長的隨機金鑰」與「綁定牌組的承諾（commitment）」上，不能靠隱藏公式或固定字串。** 固定字串仍保留作為「領域分隔」（domain separation，避免與其他用途混用），但不當成秘密。

## 二、建議方案（已實作）

```
ID   = 參賽 ID（去空白、轉大寫）
K    = 瀏覽器隨機產生 20 碼 Base32 金鑰（約 100 位元）
idx  = 牌組 25 格張數的索引（與牌組編輯器的牌組碼一一對應），7 bytes
ct   = idx XOR HMAC-SHA256(K, "CFE2026S|pad|" + ID) 前 7 bytes        → 隱藏牌組
tag  = HMAC-SHA256(K, "CFE2026S|tag|" + ID + "|" + 牌組碼) 前 16 bytes → 綁定牌組
chk  = SHA-256("CFE2026S|chk|" + ID + "|" + 本體) 前 2 碼               → 僅防抄錯
提交碼 = "S26-" + Base32(ct ‖ tag) + chk   （共 39 碼，例：S26-7QDJP-MYT69-CEAW4-N6R5V-DXBPR-6DGK8-8X3JY-ST6M）
```

* **隱藏**：沒有 K 就無法還原牌組；K 有約 100 位元，無法暴力猜。牌組空間很小也無妨，因為要猜的是 K。
* **綁定**：tag 是用 K 對「ID + 牌組碼」算出來的 128 位元值。要讓同一個提交碼用另一把金鑰解出另一副牌組，必須讓 HMAC 撞值，實際上做不到，所以不能換牌。
* **與 ID 綁定**：抄別人的提交碼掛在自己的 ID 下，因為 ID 不同而無法驗證通過。
* **四強只需金鑰**：解鎖頁輸入 ID、登錄的提交碼、選手給的金鑰，就會還原牌組碼、顯示牌表並檢查是否合法。
* **登錄檢查**：不需金鑰，只確認提交碼沒抄錯且與 ID 對應（2 碼檢查碼）。這是不洩漏牌組前提下唯一能誠實做到的檢查。牌組是否合法於解鎖時確認：官方提交頁不會為不合法的牌組產生提交碼；若有人改程式硬做，解鎖時會顯示「承諾驗證通過，但牌組不合法」，依賽規處理即可。

## 三、配套賽規建議

1. **截止後公開提交碼清單**（ID + 提交碼）。不會洩漏牌組，但可以防止任何一方事後聲稱提交碼被改過或漏登，選手也能自行核對。
2. **每個 ID 以截止前最後一次登錄的提交碼為準**，避免選手提交多份再挑選。
3. **金鑰遺失 = 無法驗牌**，建議賽規明訂處理方式（例如視同牌組不符）。提交頁提供「下載憑證檔」與「複製全部」功能，並提醒選手另存。
4. 四強驗牌時，依解出的牌表核對實體牌組。

## 四、確認提交：Google 表單收件與重新提交設計

### 為什麼用「開啟預填表單」而不是按鈕直接送出
靜態網頁確實可以在背景直接 POST 到 Google 表單，但那樣就**無法要求登入**，任何人都能用別人的參賽ID送一筆新的提交碼，把對方「最新一筆」蓋掉（對方的金鑰解不開這筆，等於被陷害）。因此「確認提交」會開啟已自動填好 ID 與提交碼的 Google 表單，選手登入 Google 後按「提交」。選手多按一下，換來身分驗證與 Google 寄出的回條。

### 建議表單設定
1. 題目只有兩題，都是簡答：「參賽ID」、「提交碼」。提交碼可加回應驗證（規則運算式 `^S26-[0-9A-Z-]+$`）。
2. 設定 → 回應 → **收集電子郵件地址：已驗證**（必須登入 Google）。
3. **寄送回應副本給填答者：一律寄送**，選手會收到含時間戳記的回條，日後有爭議可以佐證。
4. **不要**勾「僅限回覆 1 次」，也不要開「允許編輯回應」，讓每次提交都留下一筆紀錄。
5. 截止時間到就把表單切成「不接受回應」。

### 如何判定有效提交（可重新提交、又不怕被覆蓋）
* 報名時登記「參賽ID ↔ Google 信箱」。
* 截止後，每個參賽ID只採計**登記信箱所送出、時間最晚的那一筆**。用別的信箱冒名送出的紀錄直接忽略，所以不會被惡意覆蓋。
* 所有歷史紀錄都保留，有爭議時可以查。
* 把有效清單匯出成兩欄，貼到 `reveal.html` 的「批次檢查登錄格式」，一次檢查有沒有抄錯。
* 截止後公開「參賽ID + 有效提交碼」清單，供選手自行核對。

若有選手沒有 Google 帳號，可以改為報名時由主辦方發給每人一組報名 PIN，表單多一題 PIN，只採計 PIN 正確的最新一筆。兩種方式擇一即可，Google 登入比較省事。

### 把表單接上提交頁
1. 在表單編輯畫面按右上「⋮ → 取得預先填入的連結」，兩題隨便填入文字後按「取得連結」並複製。
2. 連結中會有 `entry.數字=` 兩段，分別對應參賽ID與提交碼。
3. 在 `submit.html` 開頭的 `FORM_CONFIG` 填入：
   ```js
   formUrl:   'https://docs.google.com/forms/d/e/<表單編號>/viewform',
   idEntry:   'entry.<參賽ID的數字>',
   codeEntry: 'entry.<提交碼的數字>',
   ```
   尚未設定前，按「確認提交」會顯示「提交表單尚未開放」。

## 五、GitHub Pages 部署

建議 repo 結構（例如 `cfe-2026-spring`）：

```
/index.html          → 入口（可放賽事說明與連結）
/editor.html         → 現有牌組編輯器（DeckEditer.html）
/submit.html
/reveal.html
/cfe-commit.js
/style.css
/README.md
```

在 repo 的 Settings → Pages 選擇 main 分支根目錄即可，網址為 `https://<帳號>.github.io/cfe-2026-spring/submit.html`。

建議在賽前**公告 commit hash 並鎖定程式版本**，讓選手確認程式未被修改。現場解鎖頁也可以下載成本機檔案離線使用（直接用 Chrome 開啟即可運作）。
